## Phase 14 Report

**Architecture (#97)**

* Browser-side requests only: `src/lib/api.ts` calls the backend with `credentials: 'include'` (the HttpOnly session cookie is never readable by the frontend), JSON bodies, and the backend's single error shape (`ApiError` with `code`, message and field `details`). The browser's Origin header satisfies the backend's origin check. No Server Actions and no server-side signed-in data loading.
* `src/lib/auth.tsx` — session state from `GET /api/auth/me`; any 401 signs the screen out, `PASSWORD_CHANGE_REQUIRED` re-reads the session. `RoleGate` (in `src/components/app-shell.tsx`) protects `/professor/*` and `/admin/*`: signed-out → sign-in (with a return address used only inside the account's own area), temporary password → change-password only, other role → its own home. Roles always come from the server; the backend still authorizes every request.
* `src/lib/use-resource.ts` (loading/error/reload with stale-response protection), `src/lib/format.ts` (en-IN dates in Asia/Kolkata, numbers, type and source labels), `src/lib/types.ts` (API response shapes).

### Professor onboarding by email (decision #102, Phase 14 follow-up)

The administrator no longer receives temporary passwords. Implemented with the existing Nodemailer/SMTP mailer, password generator, policy and hashing; no new dependency; one additive column.

* **Migration** `20261026120000_add_user_temporary_password_expiry`: nullable `users.temporary_password_expires_at` (still 9 tables) and a backfill giving existing professor accounts that have not changed their temporary password 7 days from the moment it runs; activated accounts and the administrator keep NULL. Applied to the test database and, with owner approval on 2026-10-26, to the development database (`npx prisma migrate deploy` in `backend/`): `migrate status` up to date and `migrate diff` empty there; the backfill gave its one unactivated professor account 7 days and left the activated accounts NULL.
* `src/services/professors/invitations.ts` — generate (CSPRNG) → store hash + expiry (7 days) → email; the plain password exists only in memory for that request. Status `SENT` (accepted by the mail server **and** still the stored password after sending), `FAILED` (send error, or superseded meanwhile), `NOT_CONFIGURED` (no SMTP). Failures log the user id and SMTP error code only. Plain-text email with the sign-in address (`CORS_ORIGIN/login`), login email, temporary password and expiry.
* Concurrency: invitation operations are serialized per professor within the process (single-instance assumption, like the sync guard); hash and expiry change in one conditional `UPDATE`; after sending, the stored hash is compared, so a superseded password is never reported as sent. Both safeguards are covered by tests that fail when the safeguard is removed.
* `src/services/professors/professors.ts` — creation and account creation email the password and return `{ professor, invitation: { status } }` (no `temporaryPassword`); `resendInvitation` (only while not activated; refuses `NO_ACCOUNT`, `PROFESSOR_INACTIVE`, `ACCOUNT_ALREADY_ACTIVE`; without SMTP changes nothing); an email change of a not-yet-activated account replaces the password in the same conditional update and emails the new address. Account detail/list add `activated` and `temporaryPasswordExpiresAt` (no secrets).
* `src/routes/adminProfessors.ts` — new `POST /api/admin/professors/:id/account/invitation` (no body; 3 per professor per 10 minutes → 429 with `Retry-After`); the mailer now reaches the admin routes (`app.ts`, `protected.ts`).
* `src/services/auth/accounts.ts` — a correct but expired temporary password is refused at sign-in and change-password with `403 TEMPORARY_PASSWORD_EXPIRED` (wrong passwords stay generic); every password change (change-password, recovery reset, admin CLI reset) clears the expiry. `src/services/email/mailer.ts` — SMTP connection/greeting/socket timeouts (10/10/20 s).

**Implemented** (`backend/`)

Rows carry sources (priority order), source-record count and relationship counts per status.

  * `updatePublication` (#90) — strict edit of title, year, venue, type family, author names and DOI; title and DOI through the shared normalizers (400 `INVALID_TITLE` / `INVALID_DOI`); a DOI owned by another publication → 409 `DOI_IN_USE` (also when a concurrent change wins the unique constraint); sets `is_curated`. Source records and relationship decisions are untouched (§9).
  * `setPublicationStatus` (#92) — ACTIVE ⇄ SUPPRESSED with `expectedStatus` (one conditional update): 409 `STATUS_CONFLICT` with the current status, 409 `INVALID_TRANSITION`, 404. Records, relationships and candidates are kept; restoring creates no relationship. Professor lists and analytics keep hiding suppressed publications (unchanged code).
* `src/services/publications/duplicates.ts`:
  * `listCandidates` (status, default OPEN, oldest first, paged; both publication summaries, a removed side is `null`) and `dismissCandidate` (conditional OPEN → DISMISSED with resolver and time; 409 `CANDIDATE_NOT_OPEN`, 404).
  * `mergeCandidate` (#93) — one transaction: claim the OPEN candidate (MERGED, resolver, time); `keepPublicationId` must be one of its two publications (400 `INVALID_KEEP_PUBLICATION`; a candidate with a removed side → 409 `CANDIDATE_INCOMPLETE`); lock both publications; ACTIVE with SUPPRESSED → 409 `MERGE_STATUS_MISMATCH` (equal statuses merge and keep that status); move the source records (match method `ADMIN`, detail naming the merge and the previous method); lock and consolidate relationships (APPROVED > PENDING > REJECTED, a tie keeps the survivor's; the winning row is kept with its id and decision metadata); re-point the removed publication's other OPEN candidates to the survivor, or close one as DISMISSED with a note when the survivor already has that pair in any status (never duplicating or reopening a pair); resolved candidates keep their history (reference NULL, §6.10); delete the merged-away publication; recompute the survivor unless curated. Any failure rolls everything back. Before its transaction the merge takes the per-title serialization (`serializeByTitle`, shared with manual entries and sync ingestion) for every normalized title of both publications and their source records, in sorted order; under the row locks it re-reads those titles and refuses with 409 `MERGE_CONFLICT` if one is not covered (e.g. a record attached by DOI meanwhile) (#96).
  * `detachSourceRecord` (#94) — one transaction with the publication locked: refuses the only record (409 `LAST_SOURCE_RECORD`); creates an ACTIVE publication from the record's fields, moves the record (match method `ADMIN`, "Detached by the administrator from publication …"), recomputes the old publication first (releasing a DOI only that record carried) and then the new one. No relationship is moved or created; a later sync gives the discovering professor a PENDING link, and rule 1 keeps the record on its new publication.
* `src/services/sync/syncService.ts` — `exclusive(operation)` (#91): refused with 409 `SYNC_ALREADY_RUNNING` while a run executes (in-process guard or a RUNNING row); exclusive operations run one at a time; `start` takes its guard synchronously and then waits for queued exclusive operations before planning the run, so a run can never start between the check and the mutation (a queued operation that finds a run pending is refused). Merge and detach use it; a scheduled run that coincides with one simply starts after it instead of failing.
* `src/services/matching/engine.ts` — `recomputeCanonical` writes only `WHERE is_curated = false` (#90), so an administrator's edit committed while a synchronization ingest is in flight is never overwritten; `ingestPublication`'s single retry now also covers a foreign-key violation (P2003) — the publication a record was matched to was removed by a merge meanwhile — so the record is matched again against the committed state (#96). Matching rules are unchanged.

## Phase 13 Report

Administrator analytics (Project_plan.md §16), computed from the stored rows on each request — no counters, caches, schema change or dependency. Backend only (screens in Phase 14).

**Implemented** (`backend/`)

  * **Default policy** (#86, #87): a publication is *counted* when it is ACTIVE (not suppressed), not a PREPRINT (canonical `type_family`), and has at least one APPROVED relationship — of any professor, active or not, as §16 states (no professor-activity condition). **Known limitations / open items**

* Owner setup: `JWT_SECRET` must be added to `backend/.env` (the backend, scripts and seed refuse to start without it); `npx prisma migrate deploy` must be run on the development database (the new migration is not applied there yet); SMTP settings are needed for recovery; the admin account must be created with `npm run admin -- create`.

* Timing: identical response bodies do not make requests indistinguishable by timing. Recovery `request` and `verify` do more database work for eligible accounts (an update, and for verify a read) than for unknown or ineligible ones, so a small timing difference remains; email is sent after responding. Evicting live entries early would let such a flood reset other clients' limits, so no cap was added; a shared store would be the deployment-grade answer if needed (Phase 16).

## Frozen Decisions (summary)

* **Data model:** 14 tables — the 9 core tables (User, Professor, ExternalIdentity, Publication, PublicationSourceRecord, ProfessorPublication, DuplicateCandidate, SyncRun, SyncTask) and, from Phase 15, CitationObservation, Journal, JournalIssn, JournalMetricSnapshot, JournalCategoryMetric (#107; the 9-table limit of #2 is superseded).
* **`ProfessorPublication.discovered_via_identity_id`:** nullable FK to ExternalIdentity, for cleanup of PENDING links from incorrect identities. No `SourceRecordProfessor`.
* **Matching:** deterministic — source+ID → DOI (with contradiction checks) → exact normalized title + year ±1 only when both years are known and the type families are compatible (same known family) → otherwise DuplicateCandidate or new Publication. Vetoes: different DOIs, preprint vs published, incompatible known types, generic/short titles.
* **Type families:** PREPRINT, CONFERENCE, JOURNAL, BOOK_CHAPTER, BOOK, OTHER (OpenAlex type combined with source/venue type).
* **Preprints:** kept separate; not auto-merged with published versions; excluded from default analytics.
* **Metadata priority:** CURATED → OpenAlex → DBLP → ORCID → Scopus → Web of Science → MANUAL (#110); curated fields protected field by field with a declared basis and evidence (`curation`, #125; refines #90).
* **Manual publications:** same pipeline; type required; never silently duplicated; DuplicateCandidate preferred over unsafe merge.
* **API response validation:** HTTP 200 is not success; HTML/malformed/error/invalid responses are fetch failures, never "zero publications".
* **OpenAlex:** validate the author identity first, cursor pagination, `per-page=100`, `select=`, retry/backoff.
* **DBLP:** SPARQL endpoint only; not pid XML, search API or mirrors; isolated client.
* **ORCID:** public API v3.0 works, JSON via `Accept` header, put-code source records, `self` identifiers only.
* **Sync:** SyncRun → SyncTask per identity; fetch → validate → normalize → match → write; one run at a time (application guard); idempotent; no deletes on missing records; node-cron is only the scheduler.
* **Sources (Phase 15):** Scopus and Web of Science as publication sources through the same pipeline; JCR for journal metrics only; licensed providers used only through institutional entitlements, with `NOT_CONFIGURED` instead of feature switches; no live Clarivate ingestion before removal tooling and written retention/deletion/backup/display confirmations (#107–#125).
* **Excluded:** AI/ML/LLM matching, embeddings, `pg_trgm`, Redis/BullMQ, microservices, GraphQL, Author table, citation graph/reference storage, author-level metrics, full paper/PDF/abstract storage, Docker/Kubernetes, OAuth/SSO, refresh tokens, hard professor deletion (initially), committing real licensed provider responses, purchases or provider agreements.
